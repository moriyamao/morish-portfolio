In-development application / source review, not a production audit

One trip. A connected workflow.

Travel planning becomes fragmented when the itinerary, spending, and support conversation live in separate places. TravelEase brings these workflows into a PHP and MySQL application with customer, staff, and administrator roles.

Customers can create, view, edit, and delete trips, organize itinerary items by day and time, and track estimated versus actual costs. Budget summaries expose planned spending, actual spending, and the remaining or exceeded trip budget.

The portfolio illustration summarizes these features; it is not an application screenshot. No public live demo is claimed.

Ownership is part of the query.

Trip access is scoped to the current customer at the database query level. A requested trip must match both its ID and the authenticated user's ID before itinerary items are read. Server-side authorization guards separate customer, staff, and admin routes.

Password-based authentication uses password hashing. Google sign-in verifies token signatures and relevant claims server-side. CSRF tokens protect state-changing forms, and session handling includes regeneration after sign-in.

These are implemented controls visible in the source, not a claim that the application has passed a comprehensive security assessment.

AI support with an exit route.

The support assistant calls the Groq API from the server. Rules escalate sensitive categories such as account security, billing, and complaints. For other TravelEase questions, the assistant can flag that a human is needed, while unrelated questions are declined.

Escalations are supported by customer and staff messaging routes. Service failures also fall back to staff escalation rather than displaying a fabricated answer. The model's self-assessment is not a calibrated confidence score, and keyword rules are not exhaustive.

What I would validate next

  • End-to-end ownership and role checks, including unauthorized trip and itinerary access.
  • Budget edge cases, invalid dates, and concurrent edits.
  • Escalation behavior for ambiguous messages and adversarial phrasing.
  • Authentication abuse controls and readiness for deployment beyond local development.

The repository's README and handoff notes lag behind several implemented features. This case study is grounded in the current trip, authentication, admin, and support source files; it does not claim unrun tests or measured user outcomes.
