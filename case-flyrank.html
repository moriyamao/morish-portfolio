Refresh & CTR-Fix Review Queue

An end-to-end ML pipeline built on anonymized production search data, used to decide which content pages a strategist should look at first — a rule baseline, a client-grouped-validated model, and a deployed research paper with a human-reviewed action playbook.

headline result: mixed, reported honestly

The problem

FlyRank's clients have large content portfolios and no easy way to know which pages need attention this week. Someone has to decide: does this page need a refresh, a CTR fix, or is it fine? Guess wrong and a team either wastes a review cycle on a page that was never the issue, or leaves a genuinely declining page unnoticed for another month. The goal was to make that weekly triage decision less of a guess, for a content strategist reading a queue — not a dashboard nobody opens.

Data

A pseudonymized 30,000-row starter slice of FlyRank's internship data warehouse — 32 clients, a trailing-90-day performance window, and a 30-day-vs-previous-30-day trend label. Client names, URLs, and private query text never appear anywhere in the work. Columns describing how content was generated (which AI provider or model) were explicitly excluded as off-topic for a performance question, and the two trend columns that define the label were excluded from the feature set to avoid leakage.

Method

I started with a hand-written rule, not a model: flag a page if it has real visibility and either it's gone stale, or it ranks fine but its click-through rate lags similar pages at that position. Before trusting either signal, I checked both against real bucket tables — staleness came back MIXED (the effect was real for well-populated tiers but reversed on a 174-row tier too small to trust), and the CTR-position relationship came back CONFIRMED, dropping cleanly as position worsened.

Only then did I try a Random Forest, trained on 13 numeric and 3 categorical features that are all knowable before the outcome. The split was grouped by client, not random — pages from the same client share hidden regularities a random split would let a model quietly memorize.

Results — model vs. baseline

On the same held-out client split, the model did not clearly beat the rule baseline. It edged ahead for small, tight review queues; the simple rule won for larger ones.

Limitations

  • Cross-sectional, one snapshot — nothing here shows a refresh causes a page to stop declining, only that staleness and decline are observed together.
  • A 32-client teaching slice, not the full ~79M-row production warehouse.
  • The model's skill is real but modest (AUC 0.600) — treated as "worth a second look," never a confidence percentage.
  • CTR-based signals can't tell a genuine content problem from a SERP feature stealing the click — that distinction still needs a human.

Ranked recommendations (the playbook)

The deployed paper's playbook blends the rule and the model into one queue, with human review built in as a requirement, not an afterthought:

  • Stale + CTR Gap pages first — both signals agree, highest confidence.
  • Stale Only and CTR Gap Only reviewed separately, one action each.
  • Model-flagged, rule silent pages routed to a human second look, never an automatic action — the model has no transparent reason code the way the rule does.
  • No page is ever auto-published, auto-edited, or auto-deleted from this queue. Pages below a minimum visibility floor never receive an automated action at all.
